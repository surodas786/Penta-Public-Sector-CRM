# Deployment, migrations and rollback (NFR-002)

**Status:** procedure written and its steps exercised locally (build,
production-mode start, migrations on clean and existing databases, backup,
restore). **Never run against staging or production** — neither exists yet.
No production deployment is authorized.

## 1. Build (in CI, never on the production host)

```bash
npm ci                         # exact versions from package-lock.json
npm run typecheck && npm run lint
npm test                       # integration suite, isolated test database
npm run test:smoke             # browser checks
npm run build                  # web (with demo-exclusion checks) + server
npm run check:production-server   # the compiled server, in production mode
```

GitHub Actions (`.github/workflows/ci.yml`) runs the same gate on every pull
request with a throwaway PostgreSQL service and synthetic credentials.

Release artefact: `dist/` (static web build), `dist-server/` (compiled API),
`package.json`, `package-lock.json`, `server/db/migrations/`. On the host:
`npm ci --omit=dev` — the runtime then contains no build or test tooling (see
the dependency notes in `docs/release/security-review.md` §2).

## 2. Release procedure

1. **Announce** the window; releases that include a migration should be
   outside working hours (Asia/Dhaka).
2. **Back up** (backup-and-restore.md §2) and confirm it completed. This is
   the rollback point for the database.
3. **Stop the job worker** if it runs separately (`JOBS_ENABLED=false`
   deployments): jobs are retryable, so stopping mid-run is safe.
4. **Migrate** as the schema owner: `npm run db:migrate` with
   `MIGRATION_DATABASE_URL`. Migrations are applied in order inside
   transactions and recorded in `drizzle.__drizzle_migrations`; an applied
   migration is never re-run (tested: `operations.test.ts`, repeat runs).
5. **Deploy** the new `dist/` and `dist-server/`, restart the API.
6. **Verify:** `GET /api/health` → 200; `GET /api/health/ready` → 200;
   `npm run jobs:run -- --check` → OK; sign in as a pilot account and open
   the dashboard; check the request log for 5xx.
7. **Restart the job worker** if separate.

## 3. Migrations

| Migration | Reversible by | Notes |
| --- | --- | --- |
| `0000`, `0001` | Restore (baseline schema, roles' grants, reference sequence) | First deployment only |
| `0002`–`0007` | The `Rollback:` steps in each file's header, or restore | All additive (columns, tables, constraints, indexes) |
| `0008` (CR4, CR5) | The `Rollback:` steps in its header, or restore | **Not compatible with the previous code**: see §3.1 |
| `0009` (CR2 email) | The `Rollback:` steps in its header, or restore | Additive; compatible with the previous code. Rolling back loses saved email settings, wording and the delivery log |

### 3.1 Migration 0008: multi-section leads and section memberships

This migration adds the `section_memberships` table and makes
`sections.lead_user_id` the source of truth for leads (ADR 0010).

**Pre-flight checks.** The migration first checks the data. It refuses to run,
and changes nothing, if any of these is true:

- an active section has no active lead;
- a lead pointer disagrees with that lead's account;
- an opportunity's section is not its owner's section.

Each refusal names the record. Fix it through the application, then run the
migration again. For example, appoint a lead, deactivate an empty section, or
transfer the record.

**Two ways to apply it:**

1. Use `npm run db:migrate` with `MIGRATION_DATABASE_URL` (the usual way).
2. Have a database administrator run the reviewed script
   `docs/operations/sql/0008_section_memberships_and_multi_section_leads.production.sql`
   with psql, as `penta_migrator`. The script:
   - runs as one transaction;
   - refuses to run twice;
   - refuses to run out of order;
   - records the migration exactly as `db:migrate` does, so a later
     `db:migrate` skips it.

   The script is generated by `scripts/ops/export-migration-sql.ts`. Never
   edit it by hand: regenerate it instead.

Both ways were rehearsed on 12 October 2026 against a scratch database at
`0007` with release-one data:

- the pre-flight check refused an active section that had no lead, and
  changed nothing;
- after that section was deactivated, the upgrade backfilled the memberships
  of both active and inactive salespeople, and installed both triggers and
  the CHECK;
- a rerun was refused;
- `db:migrate` then skipped the migration.

**Compatibility.** Unlike `0002`–`0007`, this migration cannot stay in place
under the previous release. The old code creates sections without a lead,
which the new CHECK refuses, and it reads `users.section_id`, which the new
code no longer maintains. To go back to the previous release:

1. Apply the `Rollback:` steps in the migration header.
2. Delete the migration's row from `drizzle.__drizzle_migrations`.

Do this only before any account or section has been changed through the new
code. After that, restore the pre-release backup instead.

### 3.2 Migration 0009: email delivery

This migration is additive: three tables, three enum types, and runtime grants
without DELETE. It seeds nothing and sends nothing.

Apply it with `npm run db:migrate`, or have a database administrator run the
reviewed script
`docs/operations/sql/0009_email_settings_templates_and_deliveries.production.sql`
as `penta_migrator`. The script refuses to run unless `0008` is the latest
applied migration.

It was rehearsed on 12 October 2026 on a scratch database at `0008`:

- it applied cleanly;
- the runtime role has INSERT but not DELETE;
- a rerun was refused;
- `db:migrate` then skipped it.

**After the upgrade, email stays off** until all three of these are done:

1. The deployment sets `EMAIL_TRANSPORT=smtp`.
2. The deployment sets an `EMAIL_SECRET_KEY` (32 random bytes, hex), if the
   mail server needs a password.
3. An administrator saves the mail server on the Administration page, sends a
   test email and turns delivery on.

**Rotating `EMAIL_SECRET_KEY`.** After the change the stored SMTP password can
no longer be read. The Administration page says so, and the administrator
enters the password again. Nothing else depends on this key.

### 3.3 Migration 0010: Software Procurement workflow

This migration adds the workflow column, eight stage values, the tender
phase and EOI outcome, the notice state `closed`, and the rules that tie
them together (ADR 0012). Every existing record becomes Standard; its stage,
lost reason and tenders are unchanged. The database checks the new rules
against all existing rows when they are added; release-one data passes.

Apply it with `npm run db:migrate`, or have a database administrator run the
reviewed script
`docs/operations/sql/0010_software_procurement_workflow.production.sql` as
`penta_migrator`. It runs as one transaction and refuses to run unless
`0009` is the latest applied migration.

It was rehearsed on 12 October 2026 on a scratch database brought from
`0007`, with release-one records (including a Lost one), through `0008` and
`0009`:

- the script applied cleanly;
- the existing records became Standard, with their stages and lost reason
  unchanged;
- the new stages were placed before Awarded and Lost;
- all five new rules were created;
- a rerun was refused;
- `db:migrate` then skipped it.

### 3.4 Migration 0011: Software Procurement cycles (CR6 rebuilt)

This migration replaces 0010's design (ADR 0012, revised).

- **Adds:**
  - `procurement_cycles`, with its route, milestones, EOI and RFP fields, and
    checks;
  - links from a cycle to the opportunity's contacts and documents;
  - the "Software procurement deadlines" export kind.
- **Retires 0010:**
  - drops `opportunities.workflow`, `tenders.phase` and the tender
    EOI-outcome columns;
  - adds checks that refuse the eight retired stage values and the `closed`
    notice state, which PostgreSQL cannot drop.
- **Existing records:** opportunities, tenders and documents are otherwise
  unchanged.

**Pre-flight.** The script refuses to run, and changes nothing, if any
opportunity still has the Software Procurement workflow or one of its
stages, or any tender has an EOI/RFP phase or the `closed` state. It names
each record. Correct them first. Nothing is converted automatically.

**How to apply.** Run `npm run db:migrate`, or have a database administrator
run `docs/operations/sql/0011_software_procurement_cycles.production.sql` as
`penta_migrator`. It is one transaction, and it refuses to run unless `0010`
is the latest applied migration.

**Rehearsal (12 October 2026).** A scratch database was brought to `0010`
with the code before the rebuild and filled with the synthetic test data
(23 opportunities, 8 tenders):

- a Software Procurement record planted under 0010 made the pre-flight
  refuse, naming it, with nothing changed;
- after removing it, the script applied;
- counts were unchanged, the `workflow` column was gone, and the three new
  tables existed with their grants (the runtime role cannot delete cycles);
- the export kind was added;
- a retired stage was refused by `opportunities_stage_live`;
- a rerun was refused, and `db:migrate` skipped it.

The scratch database was dropped.

### 3.5 Migration 0012: notification email events (CR2, step 6)

Additive (ADR 0011, step 6 addendum).

- **Adds:**
  - the `eoi_deadline` and `rfp_deadline` notification types, and
    `notifications.procurement_cycle_id` (the cycle an EOI or proposal
    deadline alert is about), with the subject check extended;
  - five email templates: the EOI and RFP deadline reminders, the team and
    management summaries, and the administrators' delivery-failure notice;
  - `email_notification_settings`: one row at most, the administrator's
    reminder timing, summary schedule and management summary recipients.
    The runtime role can read, insert and update it, never delete it;
  - `email_templates_security_enabled`: the invitation, password reset and
    password changed emails cannot be turned off.
- **Existing records:** unchanged. Nothing is seeded and nothing is sent.

**Pre-flight.** The script refuses to run, and changes nothing, if a
security email was turned off in Administration. It names the template. Turn
it back on there (the change is audited), then rerun.

**How to apply.** Run `npm run db:migrate`, or have a database administrator
run `docs/operations/sql/0012_notification_email_events.production.sql` as
`penta_migrator`. It is one transaction, and it refuses to run unless `0011`
is the latest applied migration.

**Rehearsal (13 October 2026).** A scratch database was migrated to `0011`.
A turned-off "Password changed" template made the pre-flight refuse, naming
it, with nothing changed. After turning it on, the script applied: the table
and its grants were created (no DELETE for the runtime role), a turned-off
reminder template kept its setting, the security check refused turning
"Password changed" off again, an EOI alert without its cycle was refused by
`notifications_subject_present`, a rerun was refused, and `db:migrate`
skipped it. The scratch database was dropped.

Rules for future migrations (unchanged from earlier milestones): additive
first; a destructive change ships in a later release after the code no
longer needs the old shape; every new table gets explicit runtime-role grants;
`audit_events` stays INSERT/SELECT only for the runtime role.

## 4. Rollback

| Situation | Action |
| --- | --- |
| New code misbehaves, migration was additive | Redeploy the previous `dist/` and `dist-server/`. Additive migrations are compatible with the previous code; leave them in place |
| A migration failed part-way | It ran in a transaction and rolled back; fix and re-run. Nothing to undo |
| A migration must be undone | Apply its header's `Rollback:` statements as the schema owner, then delete its row from `drizzle.__drizzle_migrations` — **only** if no data written since depends on it |
| Data is wrong or lost | Restore the pre-release backup into a **new** database, verify, then switch `DATABASE_URL` (backup-and-restore.md §3). Work done after the backup is lost — the RPO |

Audit events are append-only: a rollback by restore also removes audit events
written after the backup, so the release record (who, when, which backup)
must be kept outside the database.

## 5. First deployment checklist (staging, then production)

- [ ] Host, TLS certificate and reverse proxy (environments.md, hosting shape)
- [ ] PostgreSQL 18 with `penta_migrator` and `penta_app` roles, locked-down `public` schema
- [ ] Secret store populated (session, CSRF, backup key, database passwords)
- [ ] Private document storage and a real scanner — **blocked on ADR 0006**
- [ ] Identity provider / MFA decision — **blocked** (security-review.md §5)
- [ ] `npm run db:migrate`, then create the first administrator through the controlled process (FR-001), not the seed
- [ ] Monitoring wired (monitoring.md), backups scheduled and a restore drill passed on that environment
